# 用餐金额确认与同步设计

## 背景

饭搭用于记录用户日常吃饭的实际花费。菜品管理中的价格只是日常点单时的参考金额，不能强制决定某一次用餐最终花费。用户需要在点单确认时逐道菜确认本次金额，并能在日历中继续修改历史订单中每道菜的实际花费。

当前实现只有 `order_items.unit_price`、`orders.total_amount` 和 `calendar_records.amount`：

- 点单创建页直接把菜品价格作为 `unit_price`；
- 后端根据 `unit_price × quantity` 计算订单总金额；
- 订单列表又把金额除以 `100` 展示，与其他页面使用“元”的口径冲突；
- 日历只保存本餐总金额，不能展示或修改订单项金额；
- 日历编辑入口携带 `edit=1`，但页面没有进入编辑模式；
- 订单与日历同时保存总金额，但修改时没有统一同步规则。

本设计将参考金额和实际花费明确分离，并规定订单来源日历记录的总金额只能由订单项自动汇总。

## 目标

1. 菜品管理页可维护每道菜的参考金额。
2. 点单确认页可逐道菜修改本次确认金额。
3. 同一道菜数量大于 1 时，确认金额表示该订单项本次合计金额，而不是每份单价。
4. 日历可逐道菜修改订单项确认金额。
5. 订单总金额和订单来源日历总金额自动汇总，不提供直接修改入口。
6. 菜品参考金额后续变化不影响历史订单。
7. 所有金额统一使用人民币“元”，最多两位小数。
8. 金额和权限修改均具备服务端校验与自动化测试。

## 非目标

1. 不建设独立账本、支付流水或会计分录。
2. 不保留每次金额修改的历史版本。
3. 不处理多人分摊、AA 制或每位参与人的个人支出。
4. 不在本次实现饭搭投票、文件上传或完整后台管理。
5. 不允许订单来源的日历记录直接覆盖本餐总金额。
6. 不改变菜品参考金额的现有编辑入口和餐桌权限规则。

## 金额概念

| 字段 | 产品含义 | 数据来源 | 可修改性 |
|---|---|---|---|
| `dishes.price` | 菜品当前参考金额 | 菜品管理页 | 可修改 |
| `order_items.unit_price` | 下单时参考单价快照 | 创建订单时复制 `dishes.price` | 创建后不修改 |
| `order_items.confirmed_amount` | 该订单项本次合计确认金额 | 参考单价乘数量后由用户确认 | 点单确认和日历编辑可修改 |
| `orders.total_amount` | 本次订单实际总花费 | 汇总所有订单项确认金额 | 不可直接修改 |
| `calendar_records.amount` | 日历和月度统计使用的实际总花费 | 与关联订单总金额同步 | 订单来源不可直接修改 |

金额示例：

```text
菜品参考金额：20.00 元
点单数量：3
默认确认金额：60.00 元
用户修改后的确认金额：55.00 元
本餐汇总时计入：55.00 元
```

`quantity` 只参与默认值计算。用户确认后，系统不再用 `unit_price × quantity` 覆盖 `confirmed_amount`。

## 数据模型

### order_items

在 `order_items` 中新增：

```text
confirmed_amount DECIMAL(10,2)
```

Go 模型增加：

```go
ConfirmedAmount *float64 `gorm:"type:decimal(10,2)" json:"confirmed_amount"`
```

保留 `unit_price`，但将其语义固定为“下单时参考单价快照”。不复用或重命名该字段，避免历史接口语义混乱。

### 历史数据迁移

新增版本化迁移，按以下规则回填：

```text
confirmed_amount =
  CASE
    WHEN unit_price IS NULL THEN NULL
    ELSE ROUND(unit_price * quantity, 2)
  END
```

回填后：

1. 按订单汇总非空 `confirmed_amount`。
2. 更新 `orders.total_amount`。
3. 对存在 `calendar_record_id` 的订单，同步更新对应 `calendar_records.amount`。

迁移必须保持幂等，由现有迁移运行器管理版本和校验和，不修改已发布迁移。

### 空金额

菜品参考金额可以为空。订单项默认确认金额按以下规则生成：

- 有参考金额：`参考金额 × 数量`；
- 无参考金额：确认金额初始为空，用户可在点单确认页填写；
- 所有订单项确认金额均为空：订单和日历总金额为空；
- 部分订单项有金额：总金额仅汇总已填写项。

金额 `0` 是有效值，表示本次该菜未产生支出，不能与“未填写”混为一谈。

## 点单流程

### 选择菜品

点单主列表继续展示菜品参考金额。购物车中的金额在进入确认页前仅作为参考汇总，不代表最终消费。

### 确认本餐

确认面板按订单项展示：

```text
菜品名称
数量
参考单价
本次确认金额
```

每个订单项的确认金额输入框默认值为：

```text
dish.price × quantity
```

用户可以覆盖确认金额。底部“本餐总金额”只读，根据当前所有非空确认金额实时汇总。

提交请求的每个订单项包含：

```json
{
  "dish_id": "uuid",
  "quantity": 3,
  "confirmed_amount": 55.00
}
```

前端不再提交 `unit_price` 作为可信参考快照。服务端根据 `dish_id` 读取当前菜品参考金额，写入 `order_items.unit_price`；用户提交的 `confirmed_amount` 只表示本次订单项合计金额。

### 服务端创建

服务端在同一事务中：

1. 校验用户可访问目标餐桌。
2. 批量读取订单涉及的菜品并校验其归属和删除状态。
3. 将数据库中的 `dishes.price` 写入 `order_items.unit_price`。
4. 将用户确认值写入 `order_items.confirmed_amount`。
5. 汇总订单项确认金额并写入 `orders.total_amount`。
6. 创建关联日历记录，将相同总金额写入 `calendar_records.amount`。
7. 创建参与人和菜篮子条目。
8. 任一步失败则回滚整个事务。

## 日历编辑

### 详情数据

订单来源的日历详情需要返回关联订单和订单项的金额编辑信息：

```json
{
  "id": "record-id",
  "source": "order",
  "amount": 55.00,
  "order": {
    "id": "order-id",
    "items": [
      {
        "id": "order-item-id",
        "dish_id": "dish-id",
        "dish_name": "番茄炒蛋",
        "quantity": 3,
        "unit_price": 20.00,
        "confirmed_amount": 55.00
      }
    ]
  }
}
```

为避免把数据库模型直接暴露成不稳定接口，handler 使用专门的响应结构组装数据。

### 编辑规则

页面通过 `edit=1` 进入编辑态。

订单来源记录：

- 展示订单中的每道菜；
- 每项确认金额可修改；
- 本餐总金额只读并实时汇总；
- 不展示可编辑的总金额输入框；
- 保存时提交订单项 ID 和确认金额。

手工补录记录：

- 没有关联订单项；
- 保留现有本餐金额输入框；
- 可以直接修改 `calendar_records.amount`。

### 更新接口

扩展日历记录更新请求：

```json
{
  "meal_type": "cook",
  "meal_period": "晚餐",
  "restaurant": "家里",
  "order_items": [
    {
      "id": "order-item-id",
      "confirmed_amount": 55.00
    }
  ]
}
```

服务端根据记录来源分流：

- `source = manual`：允许更新 `amount`，拒绝提交 `order_items`；
- `source = order`：拒绝直接更新 `amount`，允许更新关联订单项；
- 请求中的订单项必须全部属于该记录关联的订单；
- 未出现在请求中的订单项保持原值；
- 更新后重新汇总订单全部订单项，不能只汇总本次提交的部分。

订单项、订单总金额和日历总金额必须在同一事务中更新。

## 金额校验

服务端统一校验：

1. 金额必须是有限数字。
2. 金额不得小于 `0`。
3. 金额最多保留两位小数。
4. 空值与 `0` 必须严格区分。
5. 汇总结果统一四舍五入到两位小数。

前端输入限制只用于即时反馈，不能替代服务端校验。非法输入时禁止提交，并明确提示“金额最多保留两位小数”或“金额不能小于 0”。

本次继续沿用 PostgreSQL `DECIMAL(10,2)` 和当前 Go `float64` 映射，以控制改动范围。所有比较和汇总在进入数据库前统一按两位小数归一化，后续如引入支付能力再迁移为整数分或 decimal 类型。

## 权限规则

### 金额修改

- 菜品参考金额：沿用现有菜品编辑权限。
- 点单确认金额：由订单创建者在创建订单时确认。
- 日历订单项金额：沿用现有日历记录编辑权限，仅记录创建者可修改。
- 服务端不能只依赖前端隐藏入口，必须校验记录、订单和订单项关联关系。

### 饭搭成员移除

本批同时修复饭搭成员权限残留。移除成员时必须在同一事务内：

1. 校验操作者是目标饭搭组的 `owner` 或 `admin`。
2. 禁止移除自己。
3. 删除对应 `buddy_members` 记录。
4. 找到 `type = buddy` 且关联该饭搭组的餐桌。
5. 删除对应 `table_members` 记录。
6. 任一步失败则回滚。

移除成功后，目标成员不能再访问该餐桌的菜品、订单、日历、心愿、菜篮子和预算。

## 订单列表餐桌选择

删除 `h5-personal-table` 伪 ID。

进入订单列表时：

1. 读取用户真实餐桌列表。
2. 优先使用仍然存在的 `last-order-table-id`。
3. 缓存无效时选择 `personal` 或 `couple` 餐桌。
4. 再没有时选择第一个可访问餐桌。
5. 没有任何餐桌时展示空状态，不请求订单接口。

订单金额和订单项金额均直接按“元”显示，删除现有 `/ 100` 换算。

## 错误处理

| 场景 | 服务端行为 |
|---|---|
| 金额为负数 | 返回 `400` |
| 金额超过两位小数 | 返回 `400` |
| 金额不是有限数字 | 返回 `400` |
| 日历订单项不属于关联订单 | 返回 `400`，提示请求包含无效订单项 |
| 订单来源记录直接提交总金额 | 返回 `400` |
| 手工记录提交订单项金额 | 返回 `400` |
| 无权编辑日历记录 | 返回资源不存在 |
| 饭搭成员不存在 | 回滚并返回成员不存在 |
| 餐桌成员权限撤销失败 | 回滚，不删除饭搭成员 |

前端保存失败时保留用户输入，不退出编辑态，并展示后端错误文案。

## 测试设计

### 后端服务测试

覆盖：

1. 创建订单时从菜品读取参考单价快照。
2. 用户确认金额不等于参考金额时按确认金额保存。
3. 数量大于 1 时确认金额按订单项合计值保存，不再次乘数量。
4. 多个订单项正确汇总订单和日历总金额。
5. 空金额和 `0` 正确区分。
6. 负数、超过两位小数和非法数字被拒绝。
7. 日历修改单个订单项后重新汇总全部订单项。
8. 日历修改失败时订单项、订单和日历全部回滚。
9. 订单来源记录不能直接修改总金额。
10. 手工记录仍可直接修改本餐金额。
11. 移除饭搭成员后 `CanAccessTable` 失败。
12. 权限同步失败时 `buddy_members` 删除回滚。

### 迁移测试

覆盖：

1. 新列存在且类型正确。
2. 历史 `unit_price × quantity` 正确回填。
3. 订单和日历总金额按回填结果同步。
4. 空参考价不会被错误回填为 `0`。

### 前端测试

覆盖：

1. 确认金额默认按参考价乘数量生成。
2. 用户修改确认金额后总金额实时更新。
3. 订单列表不再除以 `100`。
4. 日历订单记录逐项编辑并只读展示总金额。
5. 手工记录仍显示可编辑总金额。
6. 无真实餐桌时订单列表不发送请求。
7. `edit=1` 能正确进入编辑态。
8. 类型检查和 ESLint 通过。

## 验收标准

1. 用户可以在菜品管理页修改参考金额。
2. 点单确认页为每道菜提供本次合计确认金额输入。
3. 数量大于 1 时不会对用户确认金额再次乘数量。
4. 点单成功后订单总金额与日历金额一致。
5. 日历可逐道菜修改订单确认金额，并自动更新订单和日历总金额。
6. 订单来源日历记录不能直接修改总金额。
7. 手工补录记录仍可直接修改金额。
8. 修改菜品参考金额不会影响历史订单。
9. 全项目金额均按元展示，不存在订单列表除以 `100` 的逻辑。
10. 订单列表不再使用伪餐桌 ID。
11. 饭搭成员移除后立即失去餐桌访问权限。
12. 新增和现有自动化检查全部通过。
